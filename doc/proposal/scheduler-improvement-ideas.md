# scheduler.py 改造案（飛躍版）

作成日: 2026-08-20
対象ファイル: `scheduler.py`

現行実装（CSVポーリング + ThreadPoolExecutor + ソケットロック）を土台に、
より踏み込んだ改造案を整理する。実装コストの低い順は末尾の順序を参照。

## 1. ポーリング→イベント駆動への転換

現状は `CHECK_INTERVAL=300秒` で固定ポーリングしており、CSV編集後も最大5分
待たされる。`watchdog` で `process_schedule.csv` の変更を監視して即時反映し
つつ、内部スケジューリングは `sched` モジュールか `APScheduler` に置き換え
て「次に起こすべき最速のタスクまでスリープ」する設計にすると、応答性が上が
り無駄なCPUウェイクアップも減る。

## 2. CSV → SQLite化（データ層の刷新）

`_update_csv` の一時ファイル+リトライ方式は健全だが、並列書き込みの本質的
な脆さは残る。SQLiteに移行すればトランザクションで原子性が保証され、さらに
「実行履歴テーブル」を追加すれば成功率・平均実行時間などの統計が自然に取れ
る。CSV運用に慣れているなら、SQLiteをバックエンドにしつつ表示・編集用にCSV
エクスポート機能を残す形が現実的。

## 3. タイムアウト・リソース制限の追加

`Task.execute()` の `subprocess.run` にタイムアウトが無いのは運用上のリス
ク。暴走スクリプトがスレッドプールのワーカーを永久に占有し、他タスクの実行
を阻害する可能性がある。`timeout=` 引数の追加や、Windowsなら Job Object で
CPU/メモリ上限を課すところまで踏み込むと堅牢性が一段上がる。

## 4. 依存関係を持つワークフロー化

現状は各タスクが完全に独立しているが、「AがOKならBを実行、NGならCで通知」
のような依存グラフをCSVの新列（例: `DependsOn`, `OnFailure`）で表現できる
と、簡易Airflow的な使い方ができる。ミニDAGエンジンとして `Task` 同士の前後
関係を `Scheduler` 側で解決する形。

## 5. 失敗時の通知・自己診断

現在は失敗してもログに書くだけ。Slack/Teams Webhook通知を
`Task.execute()` の失敗パスに追加するのは小さな変更で効果が大きい。さらに
飛躍するなら、`stderr` をLLM APIに渡して「原因の要約と対処案」を自動生成し
ログに残す、という診断アシスタント化も考えられる（ただし外部送信になるの
で、送信内容にログの機密情報が混ざらないよう注意が必要）。

## 6. Windowsサービス化

現在はスタートアップフォルダへのbat登録だが、`pywin32` でWindowsサービスと
して実装すると、クラッシュ時の自動再起動やサービスマネージャからの正式な起
動/停止/再起動が可能になり、常駐運用としての信頼性が上がる。

## 7. 軽量Web UI

`process_schedule.csv` を手編集する運用から、FastAPI + 数枚のHTMLで「タス
ク一覧・手動実行・ログ閲覧・有効/無効切り替え」ができる管理画面に発展させ
ると、日常運用がかなり楽になる。認証を入れないと社内ネットワーク上でも誰で
も操作できてしまう点は要注意。
